# 인시던트 대응 러닝북 — 우리학교 모의투자

> **사고 중엔 목차를 읽을 시간이 없다.** 이 러닝북의 진입점은 항상 말미의 "증상 → 절 매핑 표".
> 절 본문은 짧게: 확인 명령 → 판단 기준 → 조치 → 확인. 사고 후 회고마다 절을 추가·수정한다 (러닝북도 실패를 먹고 자란다).

---

## §1. 공통 초동 (모든 인시던트)

1. **기록 시작**: 시각·증상·직전 변경(배포·설정)을 즉시 메모 — 조치하며 잊는다.
2. **범위 판단**: 전체 다운인가, 일부 학급/학생만인가, 교사 계정만인가.
3. **증거 보존**: Railway 로그를 조치 전에 확보 (재시작이 증거를 지운다). `railway logs` 또는 Railway 대시보드.
4. ⚠️ **상태 변경 명령(재시작·삭제·롤백) 전에**: 증거가 그 조치를 지지하는가? 패턴이 비슷해 보여도 원인이 다를 수 있다.

## §2. 가용성 장애

### §2-1. 서비스 다운 / 응답 없음
- 확인: Railway 배포 상태 대시보드, `/api/health`(또는 루트 `/`) 응답 여부, 최근 배포 시각.
- 흔한 원인 순서: 직전 배포 회귀(fail-closed 부팅 실패 — 환경변수 누락으로 서버가 exit) → 환경변수 누락(JWT_SECRET/DATABASE_URL) → Postgres 서비스 자체 장애 → Railway 인프라 장애.
- 조치: Railway 대시보드에서 직전 배포로 롤백(Redeploy 이전 성공 배포) → 로그에서 `[auth] 치명적` 등 fail-closed 메시지 확인 → 누락 환경변수 재설정 후 재배포.

### §2-2. 학생 로그인 불가
- 확인: 학급 코드가 맞는지, DB `classes`/`students` 테이블 접근 가능한지(DB 접속 불가와 겹칠 수 있음 — §2-4 먼저 배제), 서버 로그에서 로그인 라우트 에러.
- 조치: PIN 해시 검증(scrypt) 경로 이상 여부 확인 → 특정 학급만이면 해당 class_code 데이터 확인 → 전체면 §2-1(부팅/JWT_SECRET) 또는 §2-4(DB) 먼저 배제.

### §2-3. 교사 계정 탈취 의심
- 확인: 교사 로그인 시각·IP 이력(있다면), 비정상적인 교사 명령(잔액 조작·종목 강제매매) 실행 이력.
- 조치: **차단 먼저 조사 나중** — 해당 교사 계정 즉시 비활성화(`enabled=false`) 또는 비밀번호 강제 재설정. 관리자(admin) 계정이 의심되면 `ADMIN_PASSWORD` 즉시 교체 후 재배포. §3(침해 의심) 절차로 이어감.

### §2-4. DB 접속 불가
- 확인: Railway Postgres 서비스 상태, `DATABASE_URL` 환경변수 값(값 자체를 로그·대화에 노출하지 말 것), 최근 DB 서비스 재시작/마이그레이션 이력.
- 조치: Railway Postgres 서비스 재시작 상태 확인 → 볼륨 상태 확인 → 연결 문자열 재확인(비밀은 마스킹) → 서버 재배포로 재연결 시도.

### §2-5. 시세 API 중단
- 확인: 공공데이터포털 API(국내 시세), Nasdaq Trader Symbol Directory(미국 종목) 응답 여부·에러 코드.
- 판단 기준: `data/stock-universe.json`(커밋된 정적 데이터)과 런타임 캐시가 있으므로 시세 API 중단이 **거래 자체를 막지는 않는다** — 가격 갱신만 지연됨. 서비스 다운으로 오인하지 말 것.
- 조치: 외부 API 키(`PUBLIC_DATA_SERVICE_KEY`) 만료·rate limit 여부 확인 → 갱신 주기(`PUBLIC_DATA_REFRESH_MS`) 늘려 재시도 부담 완화 → 장기 중단 시 캐시된 마지막 가격으로 계속 운영 가능함을 사용자(교사)에게 공지.

### §2-6. Railway 배포 실패
- 확인: 배포 로그의 빌드/부팅 단계 에러, `Dockerfile` 빌드 실패인지 부팅 fail-closed(§2-1)인지 구분.
- 조치: 빌드 실패면 직전 성공 커밋으로 롤백 후 로컬에서 `docker build`(또는 `node --check`) 재현 → 부팅 실패면 §2-1 절차.

## §3. 침해 의심 (무단접근·유출)

1. **차단 먼저 조사 나중**: 의심 계정 즉시 비활성화. 시크릿 회전: JWT_SECRET는 §CLAUDE.md 5의 결정("운영 중 회전 금지")과 상충하지만, **침해가 확인되면 이 결정보다 우선** — 회전 후 전 사용자 재로그인 필요를 즉시 공지.
2. 영향 범위: DB 접근 로그(있다면)·최근 학생 상태 변경 이력 확인 — 닉네임 외 개인정보를 저장하지 않으므로(§CLAUDE.md 6) 유출 시에도 실명·학번 노출 위험은 낮지만, 잔액·거래 데이터 위변조 여부는 반드시 확인.
3. 법적 절차: 이 서비스는 닉네임 외 개인정보를 저장하지 않으므로 개인정보보호법상 신고 의무 대상 데이터 유출 가능성은 낮으나, 침해 확인 시 학교 관리자·담당 교사에게 즉시 통지.
4. 사후: 침해 경로 분석 → 이 러닝북 갱신 → 재발 방지 게이트 추가(예: rate limit 강화, 로그인 시도 제한).

## §4. 사후 회고 (인시던트 종료 후 필수)

- 타임라인·근본 원인·"왜 게이트가 못 막았나" → 새 게이트/절 추가 → 합리화 방지표(`docs/rationalization-guardrails.md`) 기록.

| 증상 | 절 | 첫 명령 |
|---|---|---|
| 학생 로그인 불가 | §2-2 | Railway 로그에서 로그인 라우트 에러 확인 |
| 교사 계정 탈취 의심 | §2-3 → §3 | 해당 교사 계정 즉시 비활성화 |
| DB 접속 불가 | §2-4 | Railway Postgres 서비스 상태 확인 |
| 시세 API 중단 | §2-5 | 외부 API 키·rate limit 확인 (거래는 계속 가능) |
| Railway 배포 실패 | §2-6 | 배포 로그에서 빌드/부팅 단계 구분 |
| 서비스 전체 다운 | §2-1 | Railway 배포 상태 대시보드 확인 |
| 모르는 접근·유출 의심 | §3 | (차단 먼저) |
| 위에 없는 증상 | §1 초동 후 사용자 보고 | |
